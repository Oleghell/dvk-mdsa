# Ручное ревью ответов — библиотека, ещё не живой Android-режим

## Граница этой поставки

`reply_review.py` реализует отдельное хранилище черновиков, обязательное
подтверждение каждой отправки и защиту от повторной обработки. Это **не**
готовое чтение входящих из MuMu, не новый Windows EXE и не автоматические ответы.
Кнопка «Подготовить ответы» в существующей 0.3.27 по-прежнему запускает старую
диагностику определений; для этой доработки её нажимать не нужно.

В ветке нет адаптера чтения реальных значений сообщений. Документация 0.3.26
ссылается на уже полученный приватный отчёт `rootless-reply-metadata-0.3.25.json`,
но сам отчёт в Git не хранится. Для реализации и проверки адаптера нужны
существующие определения владельцев/сигнатур идентификатора и отправителя
сообщения, коллекции истории, TextMessage и имени собеседника.
**Повторный общий сбор типов, новый проход, переустановка APK и удаление журнала
не требуются.** Сигнатуры и порядки коллекций нельзя додумывать.

## Что уже реализовано и покрыто синтетическими тестами

- Исходный `%LOCALAPPDATA%/DvkRootless/new-ten.sqlite3` открывается через
  `mode=ro` + `query_only`, с учётом SQLite WAL. Нет `Store.create`, новых
  регистраций, изменений схемы, очистки, снятия lock или checkpoint исходного
  журнала. У завершённой группы берутся только её существующие привязки —
  семь в текущем пользовательском отчёте, а не автоматически десять.
- Рабочее состояние находится отдельно:
  `%LOCALAPPDATA%/DvkRootless/reply-review.sqlite3` и возможные `-wal`/`-shm`.
  Отсутствующий исходный журнал не создаётся. Незавершённый или изменившийся
  состав группы блокируется.
- До чтения текстов `ReviewSession` требует минимальную подтверждённую
  идентичность аккаунт/собеседник/чат и сверяет её с группой. Неизвестный диалог
  не передаётся методу чтения истории.
- Подписанный исходный ID draft-чата сохраняет смысл: из `0` или отрицательного
  значения не придумывается серверный ID. Привязка положительного ID возможна
  только после проверки пары аккаунт/собеседник и первого собственного
  приветствия именно сохранённого варианта. Затем ID фиксируется.
- `ingest` не вызывает отправку. Он проверяет стабильную полную историю,
  идентичность и хронологический порядок, готовит один черновик и сохраняет
  идентификаторы/контрольный отпечаток. Повтор того же снимка и перезапуск не
  создают повторного действия. Сырые тексты входящих в БД не записываются.
- Первое входящее даёт черновик вопроса. После подтверждения и **наблюдения
  собственного сообщения в истории**, а затем следующего входящего,
  предлагается нейтральный черновик запроса контакта. Утверждение «у меня тоже»
  без знания смысла ответа не подставляется.
- Каждая отправка требует конкретного показанного черновика и
  `approved is True`. Редактирование черновика, новые или изменённые входящие
  делают старое подтверждение недействительным. В момент подтверждения
  история читается заново; нативный адаптер дополнительно обязан проверить
  контекст непосредственно перед единственным вызовом обработчика.
- Долговременная резервация с `synchronous=FULL` фиксируется до внешнего
  действия. Сбой, потеря ответа и перезапуск не разрешают повторную отправку.
  Возврат обработчика **не** объявляется доставкой.
- Отказ от общения останавливает сценарий; нетекстовое сообщение, негативный
  ответ или ручное вмешательство требуют ручного разбора. Отказ приоритетнее
  обнаруженного контакта.
- Найденный в новом входящем телефон/Telegram-username отменяет черновики и
  завершает сценарий. Контакт — кандидат: шаблон не доказывает принадлежность
  номера отправителю. Неподписанные числовые последовательности не принимаются
  за номер автоматически.
- Контакт и имя для уведомления хранятся только в отдельной локальной очереди,
  защищённой Windows DPAPI. Нет plaintext fallback. При недоступной защите
  сценарий останавливается, уведомление помечается заблокированным.
- `notify_one` отправляет не более одной попытки для диалога через существующий
  `telegram_notify.contact_notification`. Настройки бота не читаются и сеть
  не используется, пока вызывающий код явно не передаст этот notifier.
  После таймаута результат неизвестен: слепого повтора нет. Это гарантия
  **не более одной попытки**, не гарантия доставки или exactly-once: сбой между
  фиксацией попытки и запросом может оставить уведомление неотправленным.

## Контракт адаптера и подтверждения

`VerifiedBackend` — интерфейс интеграции, не реализация Android. Его методы:

1. `identity()` — только минимальные ID, без тел сообщений.
2. `snapshot(identity)` — два стабильных замера, подтверждённая полностью
   загруженная история в хронологическом порядке; строго один личный чат.
3. `submit_reply(identity, text, trigger, snapshot_digest)` — свежая проверка
   аккаунта/собеседника/чата/истории на UIKit main thread и один вызов штатного
   обработчика. Без повторов и произвольного RPC.

`ReviewSession.read_once()` вызывает только первые два пункта и `ingest`.
Локальный UI получает черновики через `store.drafts()`, позволяет редактирование
через `store.edit()`, после отдельного пользовательского подтверждения обновляет
показанный объект `Draft` и вызывает `session.confirm(draft, approved=True)`.
Отказ от черновика: `store.reject(draft.id)`; это переводит диалог в ручной разбор.

Автопоиска собеседников, приветствий, смены города, автоподтверждения, имитации
человека, фонового старта и Android-переходов в этой библиотеке нет.

## Проверки

Из корня репозитория:

```powershell
$env:PYTHONPATH='rootless-unity'
py -m unittest discover -s rootless-unity/tests -p test_reply_review.py -v
```

Тесты используют вымышленные ID/сообщения и изолированные временные SQLite БД.
Проверяется неизменность исходной БД, семь привязок, ID draft-чата, неверная
идентичность до чтения текстов, старые подтверждения, ручные правки, повторные
события/перезапуск, сохранение до побочного эффекта, неопределённые исходы,
отказ от общения, шифрование без plaintext fallback и отсутствие повторных
Telegram-попыток. Это не тест реального приложения или Windows DPAPI.

Опциональный локальный просмотр только счётчиков, без подключения к устройству:

```powershell
py rootless-unity/reply_review.py --summary
```

Команда создаёт только отдельную БД ревью; ничего не отправляет. В JSON честно
остаётся `live_backend_available=false`. Никакой новый запуск для диагностики
не требуется от пользователя, у которого уже есть отчёт с семью привязками.

## Приватность

Журналы, их WAL/SHM, сырые снимки истории, содержимое `drafts()` и токены нельзя
прикладывать к GitHub или диагностике. БД ревью содержит ID, подготовленные
исходящие тексты и зашифрованные контакты, поэтому не является обезличенным
отчётом. `summary()` выводит только счётчики и фиксированные статусы.
