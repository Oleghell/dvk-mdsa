# Диагностика 0.1.5 — главный поток и корневое окно UIKit

Это следующий ограниченный тест после успешного IL2CPP metadata-ready в 0.1.3.
В исходном APK офлайн найдены собственные UIKit-классы (Core.dll, DV.dll,
UIKit.Unity.dll), а не стандартные Unity uGUI/TextMeshPro. Проверка ищет их
метаданные, затем пытается подтвердить главный поток и **только наличие корня**.
Это не обход дерева экрана и не готовая автоматизация.


## Исправление после отчёта 0.1.4

Ваш отчёт подтвердил главный поток, экземпляр UIKit и корневое окно правильного
класса, но завершился с cleanup-failed. Наблюдатель и временная регистрация потока
были сняты; ошибка пришлась на освобождение объектных GC handles.

В 0.1.4 была ошибка ABI **в нашем пробнике**: gchandle_new/free использовали uint32.
В Unity 6 `Il2CppGCHandle` объявлен как `void*`. На ARM64 это 64 бита; код free в
переданном libil2cpp.so также обрабатывает полный x0 как указатель. Усечение верхних
битов делало освобождение некорректным. Это не требование root и не отказ защиты.

В 0.1.5 оба направления используют opaque NativePointer, без конвертации в JS
Number/uint32. Отчёт отдельно показывает acquired/released для runtime и окна;
released означает, что API освобождения вернулся без перехваченного исключения,
а не отдельную проверку внутреннего состояния сборщика мусора.
Проверка high-bit handles в синтетической фикстуре теперь обязательна на Linux и
Windows: валидные адреса выше 32-битного диапазона должны вернуться в free целиком,
число живых handles и число неверных освобождений должны остаться нулевыми.

**Перед повторным тестом перезапустите только тестовый MuMu #4**, затем откройте
установленное тестовое приложение. Так завершается прежний процесс с временными
ссылками. Рабочий #0 не перезапускайте. APK не удаляйте и не переустанавливайте.
Не запускайте старую диагностику 0.1.4 повторно.

## Запуск — без установки APK

1. Распакуйте новый ZIP и запустите `Dvk-rootless-diagnostics.exe`.
2. Оставьте оба MuMu включёнными: рабочий #0 (5555), тестовый #4 (5563).
3. На #4 откройте уже установленный тестовый ДругВокруг. Вход в аккаунт не нужен.
4. Выберите прежний ADB и **старую частную папку test-apks**.
5. Отметьте разрешение проверки только на #4.
6. Нажмите **«Проверить главный поток и окно — без нажатий»**.
7. Пришлите `rootless-diagnostics-0.1.5.json` рядом с test-apks. Старый отчёт 0.1.3
   не перезаписывается.

Ничего не удаляйте и не переустанавливайте. APK, его подпись и Gadget не изменены.
В публичном ZIP нет APK, ключей или токена; старый комплект нужен для локальной
аутентификации и проверки хешей. Рабочий #0 не изменяется.

## Что именно теперь выполняется

Режим 0.1.5 включается только отдельным entrypoint `diagnose_uikit.py` и явным
нажатием кнопки после согласия. Старый entrypoint 0.1.3 остаётся metadata-only.

1. Сохраняются прежние проверки разных устройств, фиксированного приватного
   APK-комплекта, loopback forward и единственного аутентифицированного процесса.
2. Выполняется ограниченный поиск метаданных по подтверждённому UIKit-каталогу.
3. Через C API проверяются флаги, число параметров и kind возвращаемого типа:
   boolean для проверки потока, class для runtime/окна, void для кадровых методов.
4. Временно, с **бюджетом ожидания 8 секунд и лимитом 10 000 вызовов**, наблюдается только экспорт
   `il2cpp_runtime_invoke`. Код методов и произвольные адреса не вычисляются.
   MethodInfo используется как непрозрачный handle; никаких guessed offsets.
5. Наблюдатель ждёт естественного вызова одного из трёх фиксированных методов:
   `UIRuntimeComponent.Update`, `UIRuntime.OnUnityUpdate` или
   `UnitySynchronizationContext.ExecuteTasks`. Сам их не вызывает.
6. После возврата из такого вызова проверяется отсутствие managed-исключения и
   существующая регистрация IL2CPP-потока. Первым managed-вызовом выполняется
   **только `UIRuntime.get_IsOnMainThread`**, предназначенный для проверки потока.
   При false немедленный отказ — никаких getter runtime/окна с чужого потока.
7. Только при true вызываются `get_OptionalInstance` и затем `get_MainWindow`.
   Проверяется non-null и совместимость runtime-классов возвращённых объектов.
   Временные сильные GC handles освобождаются в finally. Объекты не сохраняются
   для будущих RPC и не раскрываются в отчёте.
8. Собственный listener снимается. Не используются replace, detachAll, запись
   аргументов/возвращаемых значений или обход проверок приложения.

**Максимум три managed-вызова:** проверка потока и два getter. Пробник не читает
текст, имена/значения живых UI-объектов, профили или переписки, не перечисляет
дочерние элементы и не выполняет команды изменения UI, сообщения или покупки.
Геттеры — исполняемый код приложения, а не полностью пассивное чтение; полное
отсутствие внутренних служебных эффектов не обещается.

## Риски и ограничения

Временное наблюдение native API добавляет нагрузку. При несовместимости libnb/
Frida возможны замедление, зависание или сбой **тестового** приложения. Не отключайте
защиту Windows, не включайте root и не публикуйте порт Gadget в сеть.

Таймер ожидания не гарантирует прерывание зависшего нативного/managed-вызова.
Общий отменяемый RPC ограничен 20 секундами, очистка соединения — отдельным бюджетом.
«Отменить» не означает мгновенное прерывание нативного кода; дождитесь завершения.
При сбое не повторяйте тест многократно: пришлите отчёт, если он появился, и
опишите поведение приложения. Автоматического повторения root RPC нет.

Под libnb Unity может вызывать кадры другим путём, не через наблюдаемый экспорт.
`callback-timeout` тогда **не означает отсутствия UI или невозможности обхода**;
он означает только, что этот наблюдатель не получил подтверждённый callback.
При ошибке hook нет перехода к произвольным адресам, OCR или координатам.

`root-ready` означает: подтверждены главный поток, экземпляр UIKit runtime и
корневое UIWindow. Это **ещё не** дерево элементов, проверка доступности кнопок,
нажатия, ввод или успешный пользовательский workflow.
Другие результаты различают отсутствие runtime/окна, неправильный поток,
несовместимую сигнатуру/класс, managed-исключение и ошибку очистки.

Отчёт содержит фиксированные stage/flags/counters и метаданные из whitelist.
Нет токенов, адресов памяти, thread IDs, PID, сырых исключений, путей или UI-текста.
Работа ведётся только с #4, после проверки отличия от #0. Нет root, OCR, скриншотов,
координатных нажатий, произвольного чтения полей/heap, ADB установки/удаления/
очистки/запуска/остановки и обхода integrity/auth/certificate-проверок.

## Проверки разработчика

Unit-тесты проверяют opt-in, совместимость metadata-only режима, приватность
отчёта, запреты ADB, новый файл отчёта, строгие result-схемы и отсутствие UI actions.
Нативная синтетическая C-фикстура в собственном дочернем процессе проверяет реальный
Interceptor, guarded runtime_invoke, главный/чужой OS-поток, null runtime/window,
неверный класс, managed/исходное кадровое исключение, timeout, неверную сигнатуру
и освобождение handles. В APK/EXE фикстура не включается.
Тесты запускаются на Linux и Windows; frozen GUI self-check не контактирует с Android.
**Запуск в MuMu/ARM-трансляции всё ещё должен быть подтверждён вашим отчётом.**
