# Проверка недостающих сигнатур 0.3.28 — без переписки и отправок

## Для чего

Офлайн-отчёт `rootless-chat-metadata-0.3.27.json` подтвердил Message.get_Id,
Message.get_SenderId, Chat.get_Id, DialogOpponent, CurrentUserId и User.get_Name.
В нём нет определения TextMessage.get_Text; фактический generic-тип элементов
MessagesCM/BaseDataList остаётся unresolved. Ранее сохранённый runtime-отчёт
0.3.25 сейчас недоступен.

Этот отдельный инструмент проверяет только **7 фиксированных классов и 23
нужные сигнатуры**, включая фактическую цепочку родителей коллекции истории,
тип get_Item(Int32), AllIsLoaded и владельца унаследованного get_Value.
Это не повторный общий инвентарь типов. Неизвестные generic-типы не подменяются
выдуманным Message, а PreviewText не подменяет полный текст сообщения.

## Что сделать

1. Скачай `Dvk-reply-contract-0.3.28-windows-x64.zip` из успешного отдельного
   prerelease **rootless-reply-contract-v0.3.28** или одноимённый Windows-артефакт
   успешного запуска workflow **Build read-only reply contract checker 0.3.28**.
   Обычный Code → Download ZIP не содержит готовый EXE.
2. Распакуй в новую папку. Старую программу закрой. Прежнюю папку `test-apks`
   оставь на месте — её не нужно переносить в GitHub или присылать целиком.
3. Оба MuMu оставь включёнными. На тестовом #4 / 5563 уже должно быть запущено
   существующее тестовое приложение. Достаточно экрана поиска; открывать чат,
   анкету или менять город не нужно.
4. Запусти **Dvk-reply-contract.exe**. Проверь путь к `adb.exe` и выбери прежнюю
   папку `test-apks`. Не выбирай новую пустую папку и не создавай новые APK.
5. Нажми **«Проверить сигнатуры · без сообщений»** один раз.
6. Пришли **`rootless-reply-contract-0.3.28.json`**, созданный рядом с выбранной
   папкой `test-apks`. Кнопка «Отчёт» открывает именно отчёт этого запуска.

Нельзя повторять «Новую десятку», удалять журнал/lock, переустанавливать APK или
собирать общий инвентарь через старую кнопку «Подготовить ответы» ради этой
проверки. Существующие семь привязок остаются на месте. Токен Gadget берётся
локально существующим проверенным механизмом; в отчёт он не включается.

Если Windows запрещает запуск, не отключай защиту и не меняй политики ради
обхода. Нужен разрешённый способ запуска на твоём устройстве.

## Какие действия выполняются

Сохранены прежние preflight-проверки различия #4 / 5563 и рабочего #0 / 5555,
проверка локального bundle и аутентифицированное соединение с одним Gadget.
ADB использует прежний ограниченный набор read-only диагностических команд и
локальный временный forward к Gadget; созданный forward удаляется при очистке.

Внутри IL2CPP вызываются **только экспортированные API метаданных**: поиск
фиксированных классов/методов, их владельцев, типов возврата/параметров и цепочек
родителей. Нет runtime_invoke, чтения полей/объектов, GC handles, frame hooks,
скриншотов, OCR, обхода анкет, открытия чатов, ввода или отправки сообщений.
Нет чтения SQLite-журнала и настроек Telegram; сеть Telegram не используется.

Лимиты: не более 12 000 API-вызовов, 5 секунд на определения, 2048 assembly и
10 звеньев на цепочку родителей; нет бесконечных ожиданий/автоматических UI-повторов.
Проверка выполняется на присоединённом IL2CPP-потоке; собственное присоединение
обязательно освобождается, уже существующее не отсоединяется.

## Как понимать результат

- `contract-ready`: все нужные определения и сигнатуры подтверждены. Это
  **ещё не** доказательство порядка истории или готовности живых ответов.
- `contract-incomplete`: конкретная сигнатура отсутствует или не совпала. В
  `gadget.native_metadata.checks` есть фиксированная метка и причина отказа.
- `contract-stopped` / `stopped`: ограничение, транспорт, неподдержанная среда
  или ошибка проверки; никаких догадок вместо данных.

В любом случае `method_values_read=false`, `history_read=false`,
`ui_actions_attempted=false`, `messages_sent=0`. Флаги
`chronological_order_verified=false`, `live_replies_available=false` не дают
объявить определение типов готовой автоматизацией.

В отчёте только определения типов/сигнатур и технические статусы, без тел
сообщений, имён пользователей, контактов, локального журнала и ключей.
Прежде чем пересылать любой отчёт, просмотреть его локально всё равно полезно.

## Проверки разработчиком

Unit-тесты проверяют строгую схему, отсутствие посторонних полей, запрет UI и
отправляющих режимов, новый отчёт, очистку транспорта и запуск GUI только кнопкой.
Собственный C ABI-стенд моделирует правильные/неполные сигнатуры, неразрешённый
VAR, неверный owner/параметр, byref, цикл родителей, ошибку thread attach/detach
и повреждённую метаинформацию. Canary-счётчики подтверждают ноль вызовов
runtime_invoke, field_get_value и gchandle_new.

Отдельный CI собирает Windows EXE и запускает его реальное Tk self-check без
ADB, Android и аккаунта. Пакет содержит только EXE, инструкцию и manifest с
SHA256/commit. В prerelease нет APK, токенов, журналов и отчётов пользователя.
Успех синтетических тестов и Windows packaging не заменяет первый запуск
проверки на реальном MuMu пользователя.
