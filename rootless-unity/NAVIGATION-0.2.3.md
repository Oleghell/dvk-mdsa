# ДругВокруг 0.2.3 — поиск → фильтры → отмена без OCR/root

## Что исправлено

Отчёт пользовательского запуска 0.2.2 подтвердил выбранную вкладку поиска и завершение `ShowSearchSettings()` без managed-исключения. Затем `HasPresentedViewControllers()` сообщил об окне, а `UIWindow.GetLastPresentedView()` вернул null. Подтверждения карточки фильтров, отмены и возврата не было. Повторять 0.2.2 не нужно; увеличение таймаута не исправляет этот путь.

В 0.2.3 читается **коллекция контроллеров**, а не картинка экрана:

- `UIViewController.PresentedViewControllers` — проверенный по метаданным reference-тип `Core.Collections.ReadOnlyList<UIViewController>`;
- обход начинается с RootViewController, не пропуская принадлежащие корню окна;
- у каждого известного активного контроллера представленное окно имеет приоритет перед содержимым контейнера/вкладки;
- `HasPresentedViewControllers()` учитывает ближайшего владельца представления. При необходимости используются его getter `NearestPresentingViewController` и реальная коллекция;
- проверяются точный runtime-класс коллекции, невложенный reference receiver, owner/arity/static/return/byref методов, параметр **Int32** у `get_Item`, возврат UIViewController и virtual dispatch через IL2CPP API;
- разрешена только **одна** карточка в каждой коллекции. При нескольких программа останавливается: порядок стека не угадывается;
- Count и идентичность элемента проверяются повторно в том же кадре; циклы, смена карточки, исключения, неизвестный экран или сигнатура запрещают дальнейшие действия.

Таймаут не увеличен. Сохранены проверки UIView: HasView, не скрыт, доступен для взаимодействия, Parent-цепочка достигает текущего MainWindow. IsPresented остаётся диагностикой, не универсальным условием видимости вкладки.

Это **семантический backend UIKit внутри Unity IL2CPP**, не Android Accessibility/UI Automator. Используются существующие UI-обработчики приложения, не физические клики. В этом workflow нет OCR, скриншотов, Computer Vision, фиксированных координат или root. Старые OCR-модули других режимов репозитория этим выпуском не удаляются и здесь не запускаются.

## Разрешённый сценарий

Только тестовая копия на **MuMu #4 / 127.0.0.1:5563**:

1. На естественном Unity UI-кадре проверяется основной поток.
2. Находится активный точный SearchTabController и проверяется его View.
3. Один раз вызывается `ShowSearchSettings()`.
4. На последующих кадрах находится точный SearchSettingsCardController, проверяется готовность и сохраняется идентичность.
5. В отдельном кадре повторно подтверждается та же карточка и возможность закрытия; один раз вызывается `CardViewController.DismissWithCancel()`.
6. Подтверждается возврат к **тому же экземпляру** исходного поиска. Только все эти условия дают `navigation-ready`.

Нет Apply/Reset, выбора фильтров, чтения текстов/переписок, сообщений, подарков, покупок или произвольного action RPC. При начальном экране фильтров/профиля/чата программа не пытается угадывать путь назад.

## Как запустить

1. Если после 0.2.2 остались фильтры — закройте их вручную **крестиком, не галочкой**.
2. Распакуйте `Dvk-rootless-navigation-0.2.3-windows-x64.zip` в отдельную папку.
3. Запустите оба MuMu: рабочий **#0 (5555)** и тестовый **#4 (5563)**. На #4 оставьте открытую сетку анкет поиска людей, без диалогов.
4. Запустите `Dvk-rootless-navigation.exe`. Укажите `adb.exe` и **прежнюю test-apks от установленной тестовой копии**. Ничего переустанавливать или переносить из #0 не нужно.
5. Отметьте разрешение только для #4 и нажмите **«Открыть фильтры → отменить → проверить возврат»**. Во время проверки не нажимайте в эмуляторе.
6. Прикрепите **rootless-navigation-0.2.3.json**, созданный рядом с прежней папкой test-apks.

Рабочий #0 **не изменяется**. Доступны лишь ограниченные проверки ADB для различения устройств. Нет установки/удаления APK или переноса данных/аккаунта. При потере test-apks не подставляйте чужую папку: она содержит локальные данные подключения именно к вашей уже установленной тестовой копии.

При остановке после открытия фильтры могут остаться открыты. Закройте их вручную крестиком. Отмена в программе останавливает собственный workflow, а не закрывает произвольные окна. Не запускайте повторно вслепую при ошибке.

## Проверки и ограничения

- Unit-тесты транспорта, отчёта, защиты устройств, запретов и схем состояний.
- Синтетический C ABI стенд с настоящей Frida: в том числе root/container/search-owned модальные окна при null GetLastPresentedView, владелец вне активной контейнерной цепочки, несколько окон, неправильные Count/сигнатуры, смена идентичности, managed exception, отмена во время native getter и очистка handles. Эти тесты **не заменяют запуск на пользовательском MuMu**.
- Проверяется только указанный сценарий. Полная автоматизация анкет и сообщений не готова. Реальный успешный возврат в версии 0.2.3 ещё должен быть подтверждён пользовательским JSON.
- Наблюдение: до 16 секунд / 180 естественных UI-кадров, 6000 navigation managed-вызовов; бюджет 100 мс проверяется между вызовами. Зависший native/managed-вызов нельзя жёстко прервать этим бюджетом; возможны замедление, зависание или сбой тестового приложения.
- Контроллеры: глубина до 12; UIView.Parent до 32; до 64 временных navigation handles одновременно плюс до двух постоянных идентичностей. Все освобождаются при завершении/ошибке/отмене, включая cooperative yielding Frida во время native-вызова.
- Значения Count вне 0..8 запрещены; более одного окна запрещено без попытки выбирать первое/последнее. Отчёт содержит фиксированные категории пути, этапы, счётчики и булевы признаки; UI-тексты, аккаунты, адреса памяти, ключи и токены не записываются.
- Нет обхода авторизации, integrity, pinning или root-checks. APK, ключи и полные метаданные не публикуются.
