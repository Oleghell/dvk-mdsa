# 0.3.33 — одна подтверждённая отправка своему второму аккаунту

Добавлены **одна реальная отправка «Как дела?)» по отдельной кнопке** и локальный
просмотр/сохранение текста выбранного тестового чата. Не рассылка, не фоновый
автоответчик, не переход к новым людям и не многошаговый сценарий.

Программа работает на твоём ПК. Агент в чате не получает прямой доступ к MuMu,
переписке или локальным файлам. Тексты никуда автоматически не загружаются.

## Что сделать

1. Закрой прежний EXE и распакуй ZIP prerelease `rootless-one-chat-v0.3.33` в новую
   папку. Запусти `Dvk-one-chat-check.exe`. Выбери прежние ADB и `test-apks`.
   Ничего не переустанавливай. **Существующую привязку и базы не удаляй.**
2. В MuMu #4 / 5563 вручную открой тот же уже привязанный чат со своим вторым
   аккаунтом. Поле ввода оставь пустым, клавиатуру закрой. Подтверди галочку
   своего второго аккаунта. Не переключай экран во время операции.
3. Если нужны тексты на диске, отметь отдельную галочку **«Сохранять тексты и ID
   локально…»**. По умолчанию она выключена. Это открытый JSON без шифрования
   внутри твоего профиля Windows, не обезличенный диагностический отчёт.
4. Нажми **«2. Проверить · без отправки»** без новых сообщений. Кнопка
   **«Показать переписку локально»** откроет отдельное окно с текстами последнего
   проверенного снимка. Их порядок — порядок коллекции, НЕ подтверждённое время.
5. Со второго аккаунта вручную отправь одну новую реплику **Тест предпросмотра**.
   Дождись появления в чате, нажми «Проверить» один раз. Должен появиться новый
   тестовый черновик «Как дела?)», как в 0.3.32.
6. Нажми **«3. Отправить „Как дела?)“ · один раз»**. Сверь ID обоих своих аккаунтов
   и чата в отдельном подтверждении и разреши одну реальную отправку.
   До подтверждения кнопка ничего не отправляет. Кнопка «Проверить» тоже не отправляет.
7. Дождись результата. На своём втором аккаунте проверь вручную, появилось ли
   ровно одно «Как дела?)». Пришли только **rootless-one-chat-0.3.33.json** рядом
   с прежней папкой `test-apks` и напиши, увидел ли сообщение второй аккаунт.

Если после отправки чтение остановилось на временном/неположительном ID или
соединение оборвалось, **не нажимай отправку снова и не удаляй журнал**. Проверь
второй аккаунт вручную. Можно нажать только «2. Проверить · без отправки» после
того, как приложение стабилизировалось: это попытка наблюдения, не повтор отправки.

## Что сохраняется локально

При включённой галочке после успешного чтения сохраняется:
`%LOCALAPPDATA%/DvkRootless/one-chat-transcript.json`.

- Это **последний проверенный снимок**, а не полный архив всей переписки.
  Максимум 20 сообщений; 2048 UTF-16 единиц на текст, 16384 на снимок.
- В файле есть настоящие тексты, ID аккаунтов/чата/сообщений и отправителей.
  Нет запроса имени собеседника. Нет гарантии хронологического порядка.
- Он заменяется атомарно после проверки привязки и истории. При ошибке замены
  предыдущая копия остаётся. Не появляется при выключенной галочке.
- Снятие галочки **не удаляет уже сохранённый файл**. Удалить этот отдельный
  текстовый файл при необходимости можно самому; не путай его с SQLite-журналом.
- Шифрования нет. Используется обычный доступ профиля Windows; дополнительные
  ACL не настраиваются и безопасность от других процессов твоего пользователя
  не обещается. Не помещай в общую/синхронизируемую папку и не присылай файл.
- При выключенном сохранении тексты всё равно кратковременно присутствуют в
  памяти для чтения и локального окна. Полное стирание памяти не обещается.

SQLite `%LOCALAPPDATA%/DvkRootless/one-chat-check.sqlite3` по-прежнему хранит ID
привязки, солёные HMAC-отпечатки и фиксированные коды, **не тела сообщений**.
В новой таблице `test_manual_send` — состояние одной попытки и отпечатки исходного
снимка. Сам JSON-отчёт содержит только счётчики/коды/флаги, без текстов и ID.
`message_text_exported=false` и `message_text_in_report=false` относятся к отчёту;
`local_transcript_saved` отдельно указывает успешную локальную запись этим чтением.
При ошибке сохранения/отчёта он может быть `null`: файл уже мог обновиться,
но итог операции не подтверждён. `submission_check` содержит только проверенные
фиксированные стадии/коды native-вызова, не ID и не тексты.

## Защита от повторов и смены чата

- Нужен актуальный сохранённый тестовый черновик. Перед отправкой выполняется
  свежее чтение того же чата; весь снимок должен точно совпасть с разрешённым
  черновиком и уже учтённой историей. Если появилась другая реплика, отправка
  останавливается, старое разрешение не переносится на изменённый снимок.
- До загрузки mutating-скрипта SQLite-транзакцией резервируется единственная
  попытка. Внутри native-кода отдельный latch ставится ДО вызова обработчика.
  Повторный запуск скрипта, программы или вторая копия EXE не дают вторую попытку.
- **Лимит — одна попытка для этой сохранённой привязки, не на каждый запуск.**
  Даже если вызова не было (`not-invoked`), лимит автоматически не снимается.
  При падении/таймауте остаётся `reserved-unknown`; повтор запрещён.
- Перед native-вызовом два совпадающих снимка с интервалом >= 1 секунды,
  точная привязка, main thread, видимый актуальный личный недрафтовый чат,
  проверенные ID/авторы, разрешённый ввод и неизменные объекты проверяются снова.
  Неизвестные/неположительные ID не игнорируются. Нужна история <20 сообщений,
  чтобы осталось место для одного ответа. Не удаляй сообщения ради лимита.
- Вызывается только проверенный `OnSendText` с фиксированным «Как дела?)».
  Нет произвольного текста, редактирования поля ввода, имитации человеческой
  печати, отправки приветствий или автоматического продолжения разговора.
- Сохранены pinned APK bundle, Gadget-аутентификация, фиксированный test-only
  endpoint, boot ID до/после каждого подключения, очистка hooks/GC handles/forward.
  Нет обращения к #0 / 5555, поиска устройств, установки/запуска APK или fallback.
- Смена чата, изменённая/удалённая старая история или ошибка очистки блокируют
  подтверждение результата. После возможного вызова нельзя обещать «не отправлено».

## Как понимать результат

`manual_send_state`:
- `not-reserved`: попытка ещё не резервировалась;
- `reserved-unknown`: есть резерв, достоверного результата нет;
- `not-invoked`: валидированный native-результат исключил вызов, но лимит сохранён;
- `attempted-unknown`: вызов мог начаться, обработчик не подтвердил возврат;
- `handler-returned`: обработчик вернулся; это НЕ подтверждение доставки;
- `outgoing-observed`: последующий проверенный снимок содержит ровно одно новое
  собственное сообщение «Как дела?)» при неизменных исходных сообщениях.

Даже `outgoing-observed` не доказывает получение/прочтение вторым аккаунтом и не
устанавливает причину появления сообщения (например, параллельный ручной ввод).
Поэтому **`delivery_confirmed=false`, `messages_sent=null`** после возможного
вызова, а `outgoing_observed` — отдельный узкий признак. Окончательную проверку
получения делаешь на своём втором аккаунте. Никаких автоматических повторов.

Нет фонового старта, Telegram, контактов, старого `new-ten.sqlite3` или
`reply-review.sqlite3`. После одной попытки можно продолжать только чтение,
локальный просмотр и предпросмотр, но кнопка отправки остаётся заблокированной.

## Проверки разработчика

```sh
python rootless-unity/run_unit_tests.py
cc -shared -fPIC -O0 -pthread rootless-unity/fixtures/one_chat_fixture.c -o one_chat_fixture.so
python rootless-unity/smoke_one_chat.py ./one_chat_fixture.so
python rootless-unity/smoke_one_chat_send.py ./one_chat_fixture.so
```

Синтетические unit/ABI-тесты проверяют совместимость, резерв/перезапуск/две копии,
изменившийся чат/текст, единственный вызов, закрытый ввод, неверную сигнатуру,
исключение обработчика, неизвестный исход без повтора, наблюдение исходящего
без объявления доставки и отсутствие сырых текстов в журнале/отчёте.
Проверяются локальная запись, неверная привязка, сбой атомарной замены и отсутствие
потерянных hooks/handles. Windows CI запускает упакованный GUI без ADB/аккаунтов:
согласие и локальное сохранение выключены, кнопка отправки заблокирована.
Эти тесты **не заменяют** ручной прогон реального MuMu и второго аккаунта.
