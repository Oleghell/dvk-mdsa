# Supabase: основная база PostgreSQL

Это opt-in полное облачное хранилище, не синхронизация двух рабочих баз. После подключения основные журналы MuMu, исходы отправок, контакты, общие блокировки, `/num` и статистика работают через PostgreSQL. До подключения поведение SQLite не меняется. MoreLogin и отдельные старые диагностические журналы не переводятся автоматически.

## Соединения и история анкет (1.3.47)

После простоя от 10 секунд сессия проверяется до новой операции; мёртвая заменяется до выдачи в журнал. Ошибка SQL/COMMIT запрещает возвращать сессию в пул. Неизвестная запись не повторяется, локального fallback нет. История анкет читается согласованно без writer/advisory lock; глобальный запрет нового приветствия всё равно атомарно перепроверяется перед разрешением. При сбое profile-history JSON содержит закрытые code/operation базы, без SQL и секретов.

## Автовосстановление городов (1.3.46)

Pending-резерв восстанавливается автоматически после двух согласованных read-only снимков фактического фильтра MuMu. Короткая транзакция меняет только резервы текущего порта; контакты, приветствия, запреты и исходы отправок не сбрасываются. Чтение экрана идёт без удержания общей транзакции. Временно неподтверждённый экран вызывает ожидание с сохранением резерва, а не его удаление. Это работает с основной PostgreSQL и с SQLite; повторный импорт или переключение базы не нужны. Чужие резервы не отбираются. Ручная очистка истории больше не является обычным шагом восстановления.

## Первое подключение на Windows

1. Дождись сборки DvkAssistant **1.3.51** или новее, распакуй весь архив. Не подменяй один EXE: нужны драйвер PostgreSQL и сертификат из сборки.
2. Останови все MuMu workers, закрой другие копии программы. Не запускай старые версии после переключения.
3. Сохрани выданный личный JSON подключения на этот компьютер. Он содержит пароль отдельной учётной записи приложения: не отправляй его в GitHub, бота или публичный чат.
4. Открой **Настройки → База → Подключить Supabase**. Альтернатива: `CONNECT_SUPABASE.bat` рядом с EXE, либо `DvkAssistant.exe --supabase-setup`.
5. Выбери JSON и подтверди остановку MuMu. Не закрывай окно до завершения. Первое подключение может занять несколько минут.
6. После сообщения об успехе перезапусти DvkAssistant. Удали скачанный открытый JSON: Windows уже хранит настройки через DPAPI в `%LOCALAPPDATA%\DvkAssistant\database.dpapi`.

### Что происходит при переключении

- Программа захватывает worker/device locks всех настроенных и известных локальных портов. Если процесс работает, переключение не продолжается.
- Пока серверный набор **ещё не активирован**, берётся свежий согласованный снимок `%LOCALAPPDATA%\DvkAssistant\assistant.sqlite3`, включая подтверждённые изменения из WAL. Запись в локальную базу заблокирована на время переключения.
- Снимок остаётся как `assistant-pre-supabase-<случайный идентификатор>.sqlite3`. Исходный журнал не удаляется и не переписывается.
- Неактивная серверная копия заменяется свежим снимком внутри одной транзакции. Проверяются все строки каждой таблицы: SHA-256 с учётом типов, NULL, двоичных значений и точных float. Только затем набор становится активным.
- Если локальный файл потерял известные серверной копии исходные блокировки, авторизации или записи попыток (другая/обнулённая/более старая база), активация останавливается с `cloud-local-journal-older-than-upload`. Такое состояние не исправляется очисткой журнала.
- **Уже активную облачную базу повторное подключение не заменяет локальным файлом.** Устаревшая SQLite не должна возвращать старые статусы и разрешать повтор сообщений.
- Настройки защищаются DPAPI для текущего пользователя Windows. Защищённые payload старых контактов копируются без расшифровки: для их чтения нужен исходный Windows-пользователь и его DPAPI-ключи, а не только доступ к Supabase.

Если сбой произошёл после успешной активации, но до сохранения настройки, повторное подключение присоединится к уже активной базе без повторного импорта. При сбое раньше активации вся серверная транзакция откатывается; резервные локальные снимки остаются. Выбор облачного режима сохраняется до серверной активации: после неудачной миграции запуск будет заблокирован до её успешного повторения, а не продолжит незаметно писать в SQLite.

## Защита данных и отправок

- Отдельная закрытая схема `dvk_private`, без доступа `anon`/`authenticated`; в ней не включён публичный API для приложения. Management token, publishable key и админский пароль в EXE не нужны.
- Ограниченный login приложения: без SUPERUSER/CREATEDB/CREATEROLE. Ему нужны права создавать/читать/изменять собственные таблицы внутри выделенной схемы для новых портов и версий.
- Shared **session pooler, порт 5432**, проверка TLS `verify-full` с официальным Supabase CA. Transaction pooler 6543 намеренно не поддерживается: настройки точности/сессии не должны зависеть от случайного backend.
- Сохранены PK, UNIQUE, проверки manual_actions, ID-последовательности и исходные статусы. `unknown` не превращается в «доставлено» или «можно повторить».
- Транзакции изменений сериализуются общим advisory transaction lock в PostgreSQL. Неизвестный результат записи/commit не повторяется автоматически.
- После настройки **нет fallback на SQLite** при обрыве Интернета, недоступности Supabase, повреждении/удалении DPAPI или несовпадении набора. Операция завершается ошибкой, а не пишет в отдельную локальную базу.
- Диагностическое моделирование Chain по-прежнему изменяет только ограниченный снимок в RAM, не серверные данные.

Дополнительный маркер `database-cloud-primary.json` сохраняет выбранный облачный режим даже при потере файла пароля; вместо запуска старой SQLite потребуется восстановить настройку.

**Не удаляй database.dpapi и не запускай старую сборку как способ «вернуться назад».** Старый локальный журнал после переключения уже не содержит новых облачных исходов отправок. Для обратного переноса нужен свежий проверенный экспорт и остановка всех клиентов.

## Скорость

Чтение экрана/истории на MuMu остаётся локальным. Сохранение и проверки журнала теперь зависят от сети и расстояния до Supabase. Соединения переиспользуются внутри потока, повторная локальная SQLite-разборка известных схем избегается; это не обещание прежней задержки. Полный PostgreSQL может быть медленнее SQLite, особенно на многочисленных коротких запросах. Безопасные проверки перед отправкой не убраны ради скорости.

## Проверки разработчика

- `python rootless-unity/run_unit_tests.py` — без учётных записей/Android/облака.
- `python rootless-unity/run_native_tests.py --workers 3` — существующие ABI/native стенды.
- `python rootless-unity/smoke_cloud_database.py /private/connection.json` — opt-in реальный PostgreSQL: только session-temporary tables и отдельная тестовая advisory-блокировка, без реальных сообщений. Проверяет namespace/Chain, точность REAL, RAM preview, COPY/контрольные суммы, свежий снимок и запрет перезаписи активной базы. Не печатает JSON/пароли.

Linux-тесты не подтверждают запуск GUI/DPAPI/сборки на Windows или живой MuMu. Персональные JSON/SQLite/DPAPI не должны попадать в репозиторий и публичные артефакты.

## Сбой запуска 1.3.41: journal-initialization / OtherError

Обнови весь архив до 1.3.42 или новее, не переносы базы заново. В 1.3.41 параллельные workers могли получить таймаут общей блокировки при медленном построчном backfill контактов. Исправлены пакетная обработка, повторная инициализация и время ожидания только при startup. При очередной ошибке нужен новый last-startup.json с закрытым блоком database; не удаляй журналы/настройки облака.

Стенд `python rootless-unity/smoke_cloud_startup.py /private/connection.json` клонирует схему в пять отдельных session-temporary наборов на сервере и проверяет конкурентный startup на одной тестовой advisory-блокировке. Рабочие таблицы и реальные сообщения не изменяются.

## Сбой первого прохода 1.3.42: inbox-targets / inbox-database

Это более поздний этап, чем первоначальное подключение. В 1.3.43 исключения/receipt-кандидаты/seen IDs читаются пакетами без запросов на каждую запись под общей блокировкой. Диагностика run_preparation сохраняет закрытый database.code и database.operation в JSON. Обновление не требует повторной миграции.

Проверка smoke_cloud_startup.py теперь проходит весь host inbox до первого запроса native-навигации; навигация, AI, Telegram и отправки подменены границей/запретом и не выполняются. Это не подтверждение Windows GUI или живого MuMu.

## Общие города и первое приветствие (1.3.44)

В `dvk_private.mumu_greeting_claims` хранится общий резерв первого приветствия по `peer` (ID пользователя), а в `mumu_city_claims` — занятые/неподтверждённые города по порту. `mumu_city_used` — общая история случайной ротации. Таблицы создаются автоматически в основной базе; старые `manual_actions` каждого порта сохраняются и одноразово добавляются в общий реестр приветствий. Повторный импорт и административный токен не нужны.

Резерв приветствия не добавляет запись в `mumu_peer_blocks` и не запрещает ответы в существующей переписке. `/num`, полученный контакт и явный отказ остаются отдельным запретом общения. Не удаляй новые реестры для ускорения или исправления unknown: это может разрешить повторные действия. Пауза не освобождает город. Неподтверждённую смену проверяют вручную при остановленном порту; очистка истории поиска освобождает только его города, но никогда не резерв приветствия.

Обнови все работающие копии до одной версии. Разные программы/компьютеры координируются только если действительно используют одну основную базу; отдельные SQLite и разные Supabase datasets не образуют общий реестр.

### Сбой city-navigation в 1.3.44

В 1.3.45 исправлен контракт между общим пулом городов и native-запросом: история used ограничивается кандидатами текущего порта, а не передаётся целиком. Данные Supabase переносить повторно не нужно. Старые pending-резервы автоматически не сбрасываются: JSON validation-failed не доказывает, что неизвестный UI-переход безопасно повторять. Для уже остановившегося порта останови worker, проверь экран, выдели порт в основном окне и явно очисти историю анкет в настройках. Контакты, /num, история попыток и общий запрет повторного приветствия сохраняются.
