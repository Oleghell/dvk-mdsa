# Кандидат: нажатия при мигающем курсоре — не установленный выпуск

## Что меняется

Координатные tap/hold/swipe уже поддерживаются в ДругВокруг, но сравнение
полной картинки до и внутри Android может отклонять действие при мигании
курсора. Это объяснение механизма отказа, не доказанная диагностика конкретного
устройства: её нужно отдельно подтвердить на синтетическом Android-стенде и MuMu.

Добавлен необязательный `editor_guard` к `mumu_control_gesture`:

1. Получить новый снимок и `mumu_control_inspect`.
2. Требовать `gesture_editor_guard_supported=true` и `focused=true`.
3. Передать `editor_guard={bounds: <точные bounds>, expected_text: <точный text>}`.
   В `expected_content_sha256` в этом режиме передавать `field_context_sha256`
   из того же свежего inspect, НЕ обычный хеш полной картинки.
4. Python проверяет capability, фокус, точные bounds/text/context до резервирования.
5. Android независимо дважды проверяет фактическое нативное поле и хеш экрана
   с нормализацией только этого поля; поле проверяется также после каждого снимка.
6. После действия прочитать экран; инъекция не доказывает выбор/отправку.

Нормализация допускается только для единственного видимого focused editable
non-password поля `drug.vokrug`, размер не более 800×160. Произвольную область
маскировать нельзя. Остальные пиксели точные. Пакет, размер 900×1600, координаты
x=0..899/y=48..1599, разовое action_id, лимиты, журнал, локальное включение,
неизвестный исход/остановка и отдельное согласие на отправку/покупку сохранены.
Нет отключения защиты, слепого повтора или скрытой автоматической отправки.
При других анимациях/изменении экрана отказ остаётся возможным и корректным.
Обычный режим без editor_guard не изменился; ключи Android не получают этот режим.

## Совместимость и сборка

Старый APK НЕ поддерживает этот режим. Python отклонит запрос до нажатия, если
capability отсутствует. Нет fallback на непроверенное нажатие. Изменённый Java
исходник хранится отдельно: `control-android-next/src/...`; прежние pinned APK,
Java-исходники выпуска, подписи и контрольные суммы намеренно не менялись.
Нельзя подставлять новый исходник под прежний подписанный бинарник.

Подготовка отдельной исходной сборки из корня проекта:

```sh
python mumu-navigation/control-android-next/prepare_candidate.py out/control-candidate-source
cd out/control-candidate-source
CONTROL_VERIFY_ONLY=1 bash build.sh
```

Нужны JDK и Android SDK; ANDROID_JAR и ANDROID_BUILD_TOOLS как у существующей
сборки. Скрипт не подписывает, не устанавливает и не перезаписывает существующую
директорию. Перед выпуском обязательны Android-инструментальные тесты курсора,
изменения текста/границ/пакета/результатов, однократности и неизвестного исхода;
затем подписанная сборка тем же доверенным ключом, новые pins/DEX-проверки,
полный Windows-пакет и локально подтверждённая установка. Ключ сюда не добавлять.
В этом окружении нет javac/Android SDK; компиляция и тест на устройстве не выполнены.

## Git

Пользователь разрешил один итоговый коммит исходников и CI в текущую ветку.
Подписанный пользовательский выпуск пока не подготовлен; тестовые CI APK не распространять.


## Отдельный job CI

`candidate_android` компилирует этот Java-кандидат и собственный минимальный
стенд без сети. Временной подписью CI подписываются только три тестовых APK;
они не попадают в Windows runtime или artifacts. Стенд доказательно меняет
пиксели внутри поля, проверяет один tap, отказ при изменении текста/границ,
изменение за пределами поля и чужое приложение. Автоповтора действий нет.
В artifacts сохраняется только `candidate-result.json`. Обычный Windows-пакет
ждёт успешного кандидата, но пока содержит прежний проверенный подписанный APK;
`BUILD_INFO.json` явно указывает `cursor_stable_runtime_included=false`.
Успех этого job не заменяет подписанный выпуск и проверку на пользовательском MuMu.
